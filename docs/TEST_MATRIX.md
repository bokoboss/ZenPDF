# ZenPDF Regression Test Matrix

This matrix defines the minimum behavioral checks for modernization work. It is designed to protect both PDF correctness and the existing ZenPDF interaction model.

Legend:

- `[x]` automated in the current implementation branch
- `[ ]` target / not yet automated

## Test fixtures

Use synthetic/non-confidential fixtures committed to or generated by the test suite.

| Fixture | Purpose | Current coverage |
|---|---|---|
| generated single-page PDF | Simplest valid PDF | Browser tests |
| generated multi-page PDF | Basic merge/rotate/extract | Browser tests |
| generated mixed-size PDFs | A4/custom-size handling | Browser tests |
| generated pre-rotated PDF | Preserve and compose source rotation | Browser tests |
| generated transparent PNG | Image → PDF / mixed merge | Browser tests |
| JPEG image | JPEG → PDF | Worker implementation; dedicated browser mixed fixture pending |
| password/encrypted PDF | Graceful protected-document behavior | Typed taxonomy unit coverage; browser fixture remains pending |
| generated malformed PDF bytes | Error/recovery behavior | Browser tests |
| generated 100-page PDF | Medium performance fixture | CI benchmark |
| generated 500-page PDF | Large-document behavior | CI benchmark |
| generated 1,000-page PDF | Stress behavior | Targeted/manual CI command available; not routine |

## Core behavioral matrix

### Import and parsing

- [x] Valid PDF reports the correct page count in browser workflows.
- [x] PNG imports as one page in a mixed PNG/PDF browser workflow.
- [ ] Dedicated JPG one-page browser assertion.
- [x] Mixed PDF/image import preserves file order for the tested PNG/PDF case.
- [ ] Unsupported input is rejected without corrupting workspace state.
- [x] Corrupt/malformed PDF produces a recoverable application error and leaves the workspace usable.
- [x] Password/encrypted PDF maps to a classified, recoverable domain error; browser fixture remains pending.
- [x] Thai/non-ASCII source filename can be imported and processed.

### Quick merge

- [x] Two PDFs merge in file-list order.
- [ ] Browser drag-reordered files merge in the new order.
- [x] PDF + PNG merge successfully.
- [ ] Dedicated PDF + JPEG browser fixture.
- [x] Source page dimensions are preserved for tested PDFs.
- [x] Output page count equals the expected total for tested merge cases.

### Page editor

- [x] Editor initializes the expected page count/document order in tested workflows.
- [ ] Single-page drag changes output order correctly in browser output.
- [ ] Multi-selected pages move as a group in browser output.
- [ ] Shift-select selects a contiguous range in browser interaction.
- [x] Rotate page changes generated PDF rotation correctly.
- [x] Source-page rotation is preserved and editor rotation is additive.
- [ ] Rotate selected pages applies to all selected pages in browser output.
- [ ] Delete page removes it from parsed output.
- [ ] Delete selected pages removes all selected pages from parsed output.
- [x] Extract selected pages creates only the selected output pages.
- [ ] Add-file-from-editor appends/imports pages predictably in browser output.

### Undo/redo

- [ ] Reorder can be undone/redone in a focused automated test.
- [ ] Rotate can be undone/redone in a focused automated test.
- [ ] Delete can be undone/redone in a focused automated test.
- [ ] Group move can be undone/redone in a focused automated test.
- [ ] A new edit after undo clears redo history.
- [x] File removal/history cleanup prevents references to removed file/page state.

### Reset and lifecycle

- [x] Reset clears files/pages/output URLs in store regression coverage.
- [x] Reset terminates the active worker and starts a clean worker.
- [x] Late parsed responses for removed/nonexistent files cannot repopulate editor state.
- [x] Late thumbnail responses for removed files are rejected and their Object URLs revoked.
- [x] Removing a file releases its thumbnail/output resources and related page/selection/history state.
- [x] Generated output is invalidated/revoked when page content changes.
- [x] Duplicate save dispatch is blocked while a save is active.
- [x] Session/task-ID stale-response rejection after the typed Phase 1 protocol exists.
- [x] Explicit cancellation response behavior after Phase 1.
- [x] Worker fatal error + restart through the typed worker client.
- [x] Accepted/rejected Object URL ownership is bounded in focused lifecycle tests and deterministic repeated-cycle stress loops.
- [x] Reset races are qualified during parse, thumbnail delivery, merge, and extract operations.
- [x] Active file removal is qualified during parse/thumbnail delivery without affecting unrelated files.
- [x] Cancellation/replacement is qualified against late output and typed task errors.
- [x] Fatal worker recovery is qualified through store restart and a new parse session.

### Local UI runtime and visual qualification

- [x] Tailwind v3 utilities are emitted by the local build-time pipeline, including arbitrary values used by the application.
- [x] Built production preview has no runtime requests to Tailwind CDN, Google Fonts, or other third-party UI assets.
- [x] Landing, documents, editor, and narrow landing computed styles/layout are asserted against accepted-main evidence.
- [x] Linux Chromium screenshot comparisons use accepted pre-migration visual artifacts; local platform assertions compare accepted and migrated captures deterministically.

## Output verification

- [x] rotation

## Performance baseline

Phase 0 CI records the same blank-page benchmark on the GitHub-hosted runner environment:

| Pages | Parse | Editor ready | All thumbnails |
|---:|---:|---:|---:|
| 100 | 368 ms | 811 ms | 2,229 ms |
| 500 | 876 ms | 20,697 ms | 20,731 ms |

The 500-page result identifies a large scaling gap after page-count recognition and strongly motivates Phase 2 testing of full-grid/DnD rendering cost plus thumbnail scheduling.

Phase 2 acceptance direction:

- the main UI should remain interactive during parsing/rendering,
- visible pages should become useful early,
- large-document work should be cancellable by session/reset,
- full-grid construction should not block useful editor access for tens of seconds,
- improvements must be demonstrated against the same benchmark rather than asserted qualitatively.

See `docs/PERFORMANCE_BASELINE.md` for methodology and interpretation limits.
